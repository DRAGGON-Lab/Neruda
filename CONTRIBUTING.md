# Contributing to Neruda

Neruda follows the approved ANDES/Neruda XP + Kanban delivery policy, independently usable without ANDES installed. Human maintainers accept contributions and approve exact stable release identities. Accountable scientific authors approve publication, author information and claims. Independent build/scientific review is required for consequential changes. No reviewer or agent can waive protected evidence or permission gates unilaterally.

## Safe contributions

Public infrastructure, private research, controlled stable releases. Use synthetic and appropriately licensed examples only. Original source remains intact in LaTexProjects. Before extracting reusable code/templates, document exact source revision/path/digest, applicable terms, attribution, dependencies, adaptation, reviewer and validation status. Root MIT covers repository-owned material; third-party publisher classes, citations/sources, fonts, logos/branding, datasets, images, tools and other resources retain separate terms. Do not copy or redistribute restricted content or binary environments. Refer to controlled identifiers and versions for restricted inputs. Review institutional IP and permissions as needed. Never include secrets, private agent/learning records, unpublished data or confidential PDF/logs in the public repository or CI artifacts.

## Pull-based delivery and checks

Pull small independently verifiable changes from the unblocked dependency frontier, using the shared XP + Kanban WIP/review limits and weekly review cadence. The initial proposed limits are two implementation tasks and two awaiting review across both repos, adjusted to observed review capacity. Prefer a bounded spike and ADR when compatibility or architecture is unknown. TDD/negative checks where useful; update docs, provenance and version records as behavior changes. No blanket claim of compilation or visual success without actual receipts.

**Ready:** authorized scope, repo/revision, blockers, owner/reviewer, acceptance and expected evidence, protected inputs, source rights, applicable tool/version requirements, rigour and environment mutation permission boundaries identified.

**Done:** correct scoped artifact, verified current source and build when applicable; negative/behavioral checks; all applicable scientific/math/citation/visual/ethical checks, independent review and human acceptance; exact inputs/command/environment/log/PDF identity and omissions; docs/provenance/ADR updated; no unauthorized modifications. A missing tool is `not_run`/blocked, not a pass. A docs-only task does not imply a build passed. Stable releases additionally require compatibility notes, migration/rollback and applicable gates G0/G4 (and G8 for integrated pilot). A standalone release need not wait for ANDES autonomy or Dreaming.

## Issue and PR standard

Issue: concise title, motivation, objective, behavior/scope, dependencies, acceptance checklist, expected evidence and design/ADR links. Keep work small and independent where possible; source audit and compatibility spikes are separate from implementation. PR: why, what changed, scope/issue, meaningful tradeoffs, blast radius and reversibility, verification. For visual changes include source revision and rendered before/after evidence where available. Review findings name severity, location, trigger, impact and reproduction. Note any not-run check, unsupported platform, license or permission blocker. Do not use merge/close shortcuts for partial work. Machine-readable issue/PR templates and CI are later tasks, not part of this review-only documentation.

## Release policy

Stable versions are explicitly approved and pinned; development commits are not stable releases. Compatibility is demonstrated by standalone synthetic builds, log and rendered-page review, appropriate source licensing, documented support and rollback preserving research sources. Toolchain and publisher changes need review; installation/repair and administrative GitHub settings require separate permission. Protect release credentials and require human review/appropriate CI when settings are authorized. At bootstrap, no remote files, issues, releases or settings are changed.
